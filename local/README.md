# Local hands-free voice experiment

Open **http://localhost:8090**, click **Let’s talk**, and allow microphone access. Speak naturally; turns submit automatically after 650 ms of silence and speech plays as audio chunks arrive. Tap the same button during a response to interrupt, or while listening to end the conversation. Try:

> Please remember this in a note. My project is called Balcony Buddy. It helps people grow herbs in small apartments.

The flat pink Petal workspace has a searchable vault, editable Markdown with clickable wikilinks, and bottom feedback showing live tool activity and note excerpts. Create notes with “Plant a new note” and save manual edits with “Save note”. You can edit while talking: unsaved drafts are preserved and stale manual or voice writes are rejected using content revisions.

The local instruction model chooses tools, saves actual Markdown in `.local/vault/`, receives the result, and generates a spoken acknowledgement. Existing note versions are backed up in `.local/history/`. Exa search needs `EXA_API_KEY` in the Python app's environment.

## Startup after a restart

```sh
python3 local/setup.py
python3 local/setup_tools.py
python3 local/setup_encoder.py
python3 local/start.py
python3 local/start_tools.py
python3 local/server.py
```

The first three commands download/verify models (already completed on this machine). The next two start detached inference processes; don't repeat them while the ports are in use. The last command serves the app. Audio server: 8088; tool server: 8089; app: 8090. Logs are in `.local/audio-server.log`, `.local/tool-server.log`, and `.local/voice-lab.log` for the currently detached app.

## What is actually running

- LFM2.5-Audio-1.5B: local recognition and speech synthesis, Q4 backbone and vocoder, F16 encoder.
- LFM2.5-1.2B-Instruct Q4_K_M: structured tool selection and tool-result handling through llama.cpp.
- Python localhost app: streaming NDJSON audio/tool events and real filesystem tools.
- Browser: AudioWorklet capture, energy-based speech detection, scheduled incremental PCM playback.

The official audio runner rejects custom system instructions and supports only fixed ASR/TTS/interleaved-chat prompts. Its audio backbone also failed our text-based structured tool test. Consequently **voice + tools is ASR → tool agent → TTS**, not one native speech-to-speech model with tool calling. Native speech-to-speech mode is available for a one-turn comparison without tools.

## Measurements on this M4 / 24 GB MacBook Air

Synthetic spoken inputs generated by macOS Samantha, warm local models:

| Test | Observed result |
| --- | --- |
| Native speech-to-speech | First server audio chunk: 0.36 s after submission |
| Spoken note request, tools, streamed audio | First client audio chunk: 1.17 s after submission |
| Same note request: recognition | 0.47 s |
| Same note request: tool agent including save and follow-up | 0.61 s |
| Same note request: first TTS chunk | 0.07 s |
| Approximate end-of-speech to playback with silence detection | ~1.9 s including 650 ms turn detection and ~40 ms scheduling |
| Inference process resident memory snapshot | Audio ~1.49 GB; tool model ~0.88 GB |

Streaming tests verified real audio input, accurate recognition for the Balcony Buddy sentence, a successful `write_note`, returned tool output, and audio chunks arriving before generation finished. Browser microphone permission, capture thresholds, speaker quality, and actual playback latency need the user's microphone test. Latency varies with utterance length, note size, tool rounds, and network search.

## Current conversational limits

This prototype listens automatically again after playback. It gates speech capture while answering to avoid speaker echo; it does **not** support automatic spoken barge-in/full duplex. Tap the talk button during a response to stop playback and resume listening. Pending backend tools can still finish after interruption or disconnection.

## Friendlier voice candidates

The current output is still Liquid's Q4 TTS. Candidate upgrades, not yet auditioned locally:

- **Kokoro-82M**, starting with `af_heart`, then `af_bella`: compact local TTS with multiple voice choices. Good first experiment for a softer companion voice. Actual preference requires listening; avoid aggressively shortening sentences because the model card notes weak performance on very short utterances.
- **Qwen3-TTS-12Hz-0.6B-CustomVoice**: documented natural-language tone control, such as warm, gentle, playful delivery, with English speakers Aiden/Ryan. Test an Apple Silicon-compatible runtime and measure first-chunk latency before integration. Its advertised 97 ms is not a measurement on this Mac.
- Compare higher-precision Liquid vocoder weights and its other US/UK preset voices to determine whether artifacts come from quantization versus voice style.

A friendly pet personality also benefits from natural phrasing, restrained playful acknowledgements, sentence-aware pacing, and soft earcons for successful saves. Avoid reading paths/Markdown or pitch-shifting the voice into an artificial character. Keep tool-result speech grounded in confirmed tool outcomes.

Small-model limitations are visible: one synthetic sentence transcribed “plant reminders” as “planned reminders” with both Q4 and F16 encoders. Tool argument validation, same-turn exact-call deduplication, and read-before-overwrite enforcement are applied in the app. Tool failures are surfaced rather than voiced as successful actions.

All voices/recognition/agent inference run locally. Exa searches are external. This is a single-user localhost experiment, not an authenticated public server. Restarting the app clears conversational history but preserves Markdown notes.
